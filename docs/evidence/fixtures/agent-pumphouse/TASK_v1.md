# Puzzle/adventure workflow

The accompanying root-owned input/tool manifest identifies the exact engine, SDK, runtime, compiler profile, file roots and limits. This is one fresh Claude game-authoring session. No implementation or reference puzzle solution is supplied.

Create a first-person exploration/repair adventure from a fresh Poima project; deliver a standalone Windows export. Choose the setting, layout and solution. Aim for 5–10 minutes of ordinary play in one compact environment with a finite objective. This is design guidance, not a hidden completion-time test.

Required behavior:

- Use native movement/collision, camera-directed spatial interaction and compiled gameplay. Menus may use logical UI controls. Inventory must represent at least two useful item types, both relevant to progression, with inspectable identity/quantity and bounded authoritative storage. Supported scalar state or bounded components/collections are acceptable.
- Include two distinct persistent world changes with gameplay consequences: changed access, collision, or a usable environmental mechanism. Each change must have independently observable before/after spatial or mechanism behavior; labels and completion flags alone are insufficient. Use supported runtime mechanisms rather than assuming an arbitrary authored Collider toggle exists. At least one interaction must reject an unmet inventory prerequisite with understandable feedback, without consuming inventory or performing the world change. Repeating an already completed interaction must not duplicate rewards or repeat consumption.
- A reachable partial checkpoint must contain an already changed world, nonempty inventory, an unfinished objective, and an item still needed for the second world change. Later play must consume/install that carried item and perform the second change. Both inventory and world state must differ from the partial checkpoint.
- Provide explicit Start, pause/resume, Save, Load and New Game controls. Saving must complete before presenting success. Loading restores partial progress rather than running fresh initialization. The checkpoint is the actual durable save boundary, which can precede later completion/status UI; preserve that state rather than assuming the later success HUD was saved. New Game resets inventory, changed world and objective/UI to the initial playable state; it does not implicitly reload or delete the existing checkpoint. Require an explicit Save to overwrite it. New Game may complete its staged reset within at most 60 simulation ticks. Player pose need not return to its initial coordinates, but the reset game must be fully playable again; do not strand the player behind reset barriers. A game-owned pristine baseline is permitted if distinct from the user checkpoint. No universal engine restart API is assumed.
- Show legible objective, interaction/prerequisite feedback and inventory information. Initial, partial and completed views must remain readable at 1280×720 with UI scale 1.0. Use an actual render-capable game/player lifecycle for captures; a headless simulation alone does not prove visual output.

Use the admitted current mechanisms and matched SDK/runtime. Existing supplied licensed content and engine primitives/procedural geometry are allowed; retain source notices and verified export dependencies. Do not modify the engine, add an importer or obtain/generate new art, music or models. Discover actual capabilities rather than assuming advertised services are usable in every lifecycle.

Deliver the original project/gameplay sources, adopted native artifact, export, input/license inventory and concise PLAYTEST instructions. Include a machine-readable locator map for item/interaction entity IDs, relevant schema/field IDs, objective/world states and menu actions. Explain how to reach the required partial checkpoint and negative interaction through play. This map documents your implementation; it is not an external correctness oracle. Do not add grader-only state setters or alternate completion paths.

Run limits: one fresh Claude session, 90 minutes elapsed from starting the original provider, at most eight publication submissions and six export submissions, one heavy build/render phase at a time. Preparation and independent grading are outside this provider clock. The executor permits at most 128 script invocations, each at most 600 seconds; the supplied native transport limits each native invocation to 540 seconds. The complete case is limited to 2 GiB. Retained failed publication/export submissions count toward their respective caps; compiler diagnostics are not permission to reset the count. Retain all attempts and usage/tool records; no automatic restart or silent budget extension. Allowed assistance is the frozen general SDK/docs, capability discovery, approved MCP/file/image tools and lifecycle guidance. No task-specific code, puzzle solution, grader feedback or manual gameplay/source repair during the original run. Infrastructure failure is recorded separately; it does not authorize substituting another provider or erasing the attempt.

Read TASK.md and .refs/tools/native-tools.json first. Use normal file tools to author scripts/source and mcp__poima_executor__execute for native Windows execution; observe_image reads your existing PNG observations. Invoke Poima through the manifest native_command, which is a byte-forwarding owner of the real CLI, not an alternative engine. Do not use shell tools or invoke executables outside that owned route. Keep .refs source documents and manifests unchanged; normal compiler bin/obj outputs under its managed projects are allowed. Stop and report an uncertain/forced process outcome; never present later recovery as completion of the original workflow. Do not launch subagents or another model. Keep mutable authoritative game data in supported native-backed state/components.

Use the supplied native development profile for Native AOT publication (`development.publish`) and native export (`development.export` or `project build`); do not substitute a direct publisher/compiler invocation for these delivery steps. Budgets count distinct publication/export requests or native CLI export invocations, including rejected or failed attempts. An exact idempotent replay of the same operation is not a new submission. Ordinary discovery, build-status polling and semantic gameplay checks do not count as new publication/export submissions. If you use an authored test script, retain its actual requests/results; its assertion messages are not independent proof.
